- Product -> products -> DetalleVenta.producto, DetalleCompra.producto,
  Product.categoria (ObjectId -> Category), Product.proveedorPrincipal
  (ObjectId -> Provider) -> DELETE /api/productos/:id.
- Category -> categories -> Product.categoria (ObjectId) -> DELETE
  /api/categorias/:id.
- Provider -> providers -> Product.proveedorPrincipal, Compra.proveedor ->
  DELETE /api/proveedores/:id.
- Client -> clients -> Venta.cliente, MovimientoCuenta.cliente -> DELETE
  /api/clientes/:id.
- Venta -> ventas -> DetalleVenta.venta -> sin endpoint DELETE (solo se
  recrean detalles al editar BORRADOR via PUT /ventas/:id).
- Compra -> compras -> DetalleCompra.compra -> sin endpoint DELETE (solo
  se recrean detalles al editar BORRADOR via PUT /compras/:id).
- Los deleteMany de DetalleVenta/DetalleCompra en ventaService.js:336 y
  compraService.js:227 pertenecen al flujo normal de EDICION de borradores
  y NO fueron modificados.

2. PROBLEMAS DETECTADOS
-----------------------
- Producto: eliminacion fisica SIN ninguna validacion de referencias
  (productService.eliminar usaba findByIdAndDelete directo) -> riesgo de
  dejar detalleventas/detallecompras huerfanos (casos detectados en B.1:
  5 detalleventas y 2 detallecompras huerfanos ya existentes en la BD real).
- Proveedor: solo validaba productos por proveedorPrincipal; NO validaba
  compras (Compra.proveedor) -> compras huerfanas.
- Cliente: solo validaba movimientos; NO validaba ventas (Venta.cliente)
  -> ventas huerfanas.
- Categoria: la validacion existente consultaba { categoria: categoria.nombre }
  contra un campo ObjectId -> CastError -> la validacion estaba ROTA (hubiera
  devuelto 500 en lugar de bloquear).
- Todos los conflictos de integridad devolvian 400; se estandarizo a 409.

4. CADA ELIMINACION PROTEGIDA + CODIGO APLICADO + HTTP + MENSAJES
------------------------------------------------------------------
- Producto (productService.eliminar): antes de borrar cuenta DetalleVenta
  y DetalleCompra por producto; si cualquiera > 0 -> HTTP 409,
  "El producto no puede eliminarse porque tiene movimientos historicos
  asociados." con detalle de conteos. Si no hay referencias -> se elimina.
- Proveedor (providerService.eliminar): cuenta productos (proveedorPrincipal)
  y compras (proveedor); si > 0 -> HTTP 409, "No se puede eliminar el
  proveedor porque tiene registros historicos asociados." con conteos.
- Cliente (clientService.eliminar): cuenta movimientos y ventas; si > 0 ->
  HTTP 409, "No se puede eliminar un cliente con historial. Desactivalo en
  su lugar." con conteos. Se conservan ventas y movimientos.
- Categoria (categoryService.eliminar): validacion corregida a
  { categoria: id } (ObjectId) -> HTTP 409, "No se puede eliminar la
  categoria porque tiene X producto(s) asociado(s)."
- Controllers de delete (product/provider/client/category): ahora respetan
  error.status (409) cuando el servicio lanza error con errores.
- DetalleVenta/DetalleCompra: no existe endpoint de borrado directo; el
  unico camino de borrado es la edicion de borradores (PUT), que ya rechaza
  ventas/compras confirmadas (400 "Solo se puede editar una venta en estado
  BORRADOR.") -> la trazabilidad historica queda protegida sin cambios.
