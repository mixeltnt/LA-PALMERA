========================================================================
4. RIESGOS
========================================================================
- Spin-down en planes gratuitos (Render free duerme tras 15 min de
  inactividad: el POS tardaria 30-60 s en responder la primera peticion
  del dia). No apto para negocio en horario comercial -> pagar "always
  on" o elegir plataforma sin sleep.
- CORS mal configurado romperia login/ventas entre dominios (mitigado
  con CORS_ORIGINS correcto; probar en staging antes).
- JWT_SECRET debil actual: si se reutiliza en produccion, cualquiera
  podria firmar tokens. DEBE rotarse.
- LocalStorage/sessionStorage para el token (XSS): aceptable para este
  alcance; mitigacion futura (httpOnly cookies) requeriria cambios
  grandes de auth (fuera de estas fases).
- Rate limit en memoria (por instancia): si se escalara a multiples
  instancias habria que centralizarlo; con 1 instancia es suficiente.
- Fecha/hora: los reportes usan fecha local del servidor; definir zona
  horaria de la instancia (America/Santiago) en la plataforma.
- Sin helmet: cabeceras de seguridad basicas ausentes (X-Frame-Options,
  CSP, etc.) - riesgo bajo-medio para un sistema interno.
- El 404 de rutas SPA: el hosting estatico debe reescribir todas las
  rutas a index.html (Vercel/Netlify/Railway lo hacen con config;
  NGINX con try_files). Sin esto, /ventas recargada daria 404.
- Dependencias con avisos de audit (documentados en B.1/B.2.3):
  backend 1 HIGH dev-only (brace-expansion via nodemon), frontend 5 HIGH
  (react-router-dom 7.18.1 CSRF modo RSC - no explotable con
  BrowserRouter actual, postcss, nanoid, brace-expansion via vite).
  Recomendacion: actualizar react-router-dom a >= 7.18.2 antes de ir a
  produccion.

5. PLATAFORMA RECOMENDADA - COMPARACION
========================================================================
Criterios: simplicidad, estabilidad, costo y mantenimiento para un
pequeno negocio (1 instancia backend + frontend estatico + Mongo Atlas).

a) Vercel (frontend) + Render (backend):
   + Vercel: deploy estatico ultra simple, HTTPS automatico, gratis.
   - Render free duerme (inaceptable para POS en horario comercial);
     backend "always on" desde ~USD 7/mes. Dos cuentas/paneles que
     administrar. CORS entre dominios (configurar CORS_ORIGINS).
b) Netlify (frontend) + Render (backend):
   + Similar a Vercel; Netlify gratis con bandwidth generoso.
   - Misma limitacion de Render (sleep en free). Dos paneles. CORS.
c) Railway (frontend + backend en un solo panel):
   + Todo en uno: 1 servicio backend Node (npm start, HTTPS automatico,
     dominio propio) + 1 servicio frontend estatico (dist/).
   + Sin sleep en planes pagos basicos (aprox. USD 5/mes base, sin
     contar uso; escala de gasto predecible para 1 instancia).
   + Reescribir rutas SPA en 1 linea de config (SPA fallback).
   + Proxy de /api posible si se quiere mantener ruta relativa.
   - Menos "gratis" que Vercel/Netlify puros; dominio custom incluido.
d) VPS (Hetzner/Contabo/Oracle free):
   + Control total, costo bajo (USD 4-7/mes) o gratis (Oracle ARM).
   - Requiere mantenimiento continuo: NGINX, certificados HTTPS
     (certbot), systemd/PM2, firewall, updates, backups manuales.
   - Riesgo alto para un negocio sin personal tecnico; cualquier caida
     del servidor o error de config deriva en soporte costoso.

RECOMENDACION: RAILWAY (backend) + RAILWAY (frontend estatico) + MongoDB
Atlas (M0 free), como opcion principal por simplicidad total, sin sleep,
HTTPS automatico, un solo panel y mantenimiento minimo (aprox. USD 5/mes
+ 0 del Atlas M0). Alternativa mas barata si se acepta administrar dos
paneles: Vercel (frontend gratis) + Render backend USD 7/mes. VPS queda
descartado como primera opcion por el mantenimiento que exige.

7. PASOS PARA REALIZAR EL DEPLOYMENT (cuando el usuario lo autorice)
========================================================================
1. Crear cluster MongoDB Atlas M0 y obtener la cadena de conexion
   (usuario/password del cluster). Migrar los datos actuales: exportar
   las colecciones de la base local (mongodump o script) e importar en
   Atlas (esta migracion SI modifica la base destino - requiere
   autorizacion explicita; la base local queda intacta).
2. Generar JWT_SECRET fuerte (p. ej. openssl rand -base64 48) y definir
   las nuevas contrasenas de produccion (no mostrar en informes).
3. Crear cuenta en Railway; conectar el repositorio.
4. Railway Service A - backend:
   - Root directory: backend; Build: npm install (solo prod) o
     npm ci; Start: npm start.
   - Env vars: MONGODB_URI, JWT_SECRET, CORS_ORIGINS,
     YASNA_PASSWORD, KARLA_PASSWORD, VENDEDOR_PASSWORD (solo para el
     seed; luego pueden retirarse).
   - Generar dominio propio (https://backend-lapalmera.up.railway.app
     o custom api.lapalmera.cl).
5. Railway Service B - frontend:
   - Root directory: frontend; Build: npm install && npm run build;
   - Salida estatica: dist/; activar SPA fallback (rewrites a /);
   - Env var (si se cambia api.js): VITE_API_URL=https://<api>/api en
     build; o dejar ruta relativa "/api" y configurar proxy de /api
     hacia el servicio backend en el mismo dominio.
6. Ejecutar una vez el seed: rail run npm run seed:usuarios (o ejecutar
   contra la URL del servicio) -> crea yasna/karla/vendedor en Atlas.
7. Probar en el dominio real: login de los 3 usuarios, POS completo,
   venta normal, fiado, reportes, PWA instalable, recarga profunda de
   /ventas (SPA fallback) y HTTPS.
8. Verificar que los logs de la plataforma no imprimen secretos
   (ya garantizado por B.2.3) y que MongoDB no queda expuesto (Atlas
   por defecto bloquea acceso publico; permitir solo IP de Railway o
   0.0.0.0 con autenticacion fuerte si la plataforma lo exige).
9. Definir zona horaria America/Santiago en la instancia backend.
