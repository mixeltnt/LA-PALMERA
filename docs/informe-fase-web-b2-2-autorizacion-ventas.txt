1. PROBLEMA ENCONTRADO
----------------------
- PUT /api/ventas/:id y PATCH /api/ventas/:id/confirmar estaban registrados sin
  restriccion de rol ni de propiedad (ventaRoutes.js:45-46 en la version
  auditada): cualquier usuario autenticado podia editar o confirmar una venta
  cambiando directamente el ID, incluidas ventas de otros usuarios.
- GET /api/ventas/serie estaba accesible para cualquier usuario autenticado
  (ventaRoutes.js:41), exponiendo la serie diaria de la caja.
- El sistema YA posee un mecanismo de propiedad nativo: el modelo Venta
  almacena el campo "usuario" (ref User, requerido) y los controllers
  createVenta/updateVenta lo fijan con req.usuario._id. No fue necesario
  inventar un sistema de propiedad; solo se aplico la verificacion que faltaba.
- El frontend usa /ventas/serie unicamente en Reportes.jsx (pagina restringida
  a admin/encargada en frontend); no hay pantalla de vendedor que lo use.
  Restringir el endpoint no rompe ninguna funcionalidad existente.

2. SOLUCION APLICADA
--------------------
Unico archivo de codigo modificado: backend/src/routes/ventaRoutes.js.
- Nuevo middleware verificarPropiedadVenta():
  * admin y encargada (roles de gestion) pasan directamente (conservan sus
    reglas actuales sin obtener privilegios extra).
  * vendedor: carga la venta por ID y exige String(venta.usuario) ===
    String(req.usuario._id). Si no coincide -> 403. Si la venta no existe,
    deja pasar para que el servicio responda 404 con su mensaje normal.
- GET /ventas/serie: ahora con requerirRolPermitido(["admin", "encargada"]).
  El endpoint no fue eliminado.
- Se retiro el import de autorizarRoles (no usado en este archivo).

3. REGLAS FINALES DE AUTORIZACION
---------------------------------
- Autenticacion obligatoria en todo /api/ventas (router.use(authMiddleware)):
  sin token o token invalido -> 401; usuario inactivo -> 401.
- PUT /api/ventas/:id (editar borrador):
  * admin: cualquier venta (sujeto a reglas de negocio del servicio).
  * encargada: cualquier venta (gestion actual).
  * vendedor: solo ventas BORRADOR propias (flujo normal del POS).
  * vendedor sobre venta ajena -> 403.
- PATCH /api/ventas/:id/confirmar:
  * admin: cualquier venta.
  * encargada: cualquier venta (permiso actual conservado).
  * vendedor: solo sus propias ventas (confirmacion desde el POS).
  * vendedor sobre venta ajena -> 403 (imposible saltarlo cambiando el ID).
- GET /api/ventas/serie: solo admin y encargada; vendedor -> 403.
- POST /api/ventas (POS): sin cambios; registra automaticamente al usuario
  autenticado como responsable (venta.usuario).
- PATCH /:id/anular: se mantiene exclusivo de admin (sin cambios).
