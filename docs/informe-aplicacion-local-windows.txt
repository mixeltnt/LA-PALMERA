2. ARQUITECTURA PROPUESTA (para la fase de implementacion futura)
========================================================================
Un solo proceso Node visible + un launcher invisible:

  [Acceso directo Escritorio] -> node la-palmera.cjs (ventana OCULTA)
        |  1. verifica node y dist
        |  2. (si falta dist) ejecuta npm run build (frontend)
        |  3. lanza backend: node src/server.js (proceso hijo oculto)
        |  4. sondea http://localhost:4000/ hasta responder
        |  5. abre http://localhost:4000 en Chrome/Edge
        |  6. vigila el backend; si muere, lo relanza (reintentos+log)
        v
  Backend Express en PUERTO 4000 (0.0.0.0)
        |  /api/*  (API actual, intacta)
        |  /*      (frontend compilado: express.static(frontend/dist)
        |           + SPA fallback -> index.html)
        v
  MongoDB Atlas (MONGODB_URI del .env, intacta)

Claves de la arquitectura:
- El backend pasa a servir tambien el dist del frontend: UNA URL
  (http://localhost:4000 en el PC, http://192.168.1.90:4000 en el
  celular). Con ruta relativa /api, no hay CORS y no hay que tocar
  api.js.
- El launcher es un script Node (.cjs) SIN dependencias nuevas:
  usa child_process.spawn (windowsHide: true), fetch (Node 24 tiene
  fetch nativo) para sondeo, y guarda logs + PID en archivos.
- Cierre: segundo acceso directo "Cerrar La Palmera" que detiene el
  backend leyendo el PID guardado (Stop-Process) y el launcher termina
  al detectar que su hijo murio. Cierre limpio opcional con señales.
- Recuperacion: el launcher respawnea el backend automaticamente
  (hasta N intentos consecutivos, con espera creciente) y registra
  el motivo en logs/lapalmera.log.

3. FLUJO DE INICIO
========================================================================
1. Doble clic en "LA PALMERA" (Escritorio).
2. Launcher (oculto) verifica: node disponible, backend/.env presente,
   JWT_SECRET configurado.
3. Si frontend/dist no existe o falta index.html: ejecuta
   npm run build (frontend) - primera vez o tras cambios de codigo.
4. Lanza el backend (spawn oculto, hereda el .env).
5. Sondea GET http://localhost:4000/ cada 500 ms (max 30 s).
6. Abre el navegador por defecto (o Chrome/Edge) en
   http://localhost:4000.
7. Queda vigilando; si el backend cae, lo relanza (log de cada evento).
8. El usuario usa la app con doble clic en el icono del escritorio.

========================================================================
4. FLUJO DE CIERRE
========================================================================
1. Doble clic en "Cerrar LA PALMERA" (Escritorio).
2. El script de cierre lee logs/lapalmera.pid y ejecuta
   Stop-Process -Id <pid> (o TASKKILL /PID <pid>) sobre el backend.
3. El launcher detecta la muerte de su hijo, escribe "detenido por el
   usuario" en el log y termina por si mismo.
4. MongoDB Atlas queda desconectado por el cierre del proceso
   (sin corrupcion: la base es remota y tolerante).
5. Alternativa de emergencia: Ctrl+C o cerrar el proceso en el
   Administrador de tareas (el launcher termina igualmente).
Nota: cerrar el navegador NO detiene los servicios (comportamiento
deseado: la app sigue disponible para el celular; se detiene con el
acceso directo de cierre).

8. COMPARACION DE OPCIONES DE LAUNCHER (punto 12-13 del pedido)
========================================================================
a) .bat simple: minimo, pero muestra ventana negra (antipatico) y
   gestion de procesos/reintentos rudimentaria. Descartado como
   mecanismo principal; util solo como puente a otras opciones.
b) PowerShell (.ps1): puede ocultar ventana (powershell -WindowStyle
   Hidden / Start-Process), pero el control de procesos hijos,
   reinicios y sondeo es mas verboso que en Node; ademas depende de la
   politica de ejecucion de scripts (ExecutionPolicy) que puede estar
   restringida en el PC del negocio. Alternativa valida, no la mejor.
c) Node launcher (.cjs): RECOMENDADO. Node ya esta instalado (v24),
   sin dependencias, spawn con windowsHide:true (cero ventanas negras),
   fetch nativo para sondeo, control total de reinicio/logs/PID, mismo
   lenguaje del proyecto, facil de leer y modificar.
d) .exe empaquetado (pkg/nexe/electron): innecesario; requiere
   herramientas extra, binarios grandes y recompilacion en cada cambio.
   Descartado.
e) NSSM (servicio de Windows): gestiona el backend como servicio
   (arranque automatico al iniciar el sistema, reinicio, sin consola).
   Util SOLO si en el futuro se quiere que La Palmera arranque sin
   doble clic (al encender el PC). No necesario hoy: el requisito es
   doble clic desde el escritorio. Queda como opcion futura, no como
   dependencia actual (nssm.exe es un binario externo descargable).
f) PM2: excelente en Linux; en Windows el auto-arranque se apoya en el
   Programador de tareas, requiere instalacion global (npm i -g pm2) y
   agrega una capa que el negocio no necesita para un solo proceso.
   Descartado; el respawn del launcher cubre la recuperacion.
g) node-windows (npm): instala servicios via script; misma conclusion
   que NSSM: opcion futura, no necesaria hoy.
RECOMENDACION FINAL: Node launcher (.cjs) + (futuro, opcional) NSSM si
se desea arranque automatico al encender el PC.

10. RECUPERACION DEL BACKEND SI SE CAE (punto 16)
========================================================================
- El launcher monitorea el proceso hijo (evento "exit") y respawnea
  automaticamente con espera creciente (p. ej. 1 s, 2 s, 5 s) hasta
  5 intentos consecutivos; si falla 5 veces seguidas, escribe un error
  claro en logs/lapalmera.log y lo reintenta al volver a hacer doble
  clic (o al detectar demanda).
- Causas tipicas: crash de nodemon-less, puerto ocupado (EADDRINUSE),
  MONGODB_URI caida (Atlas). El launcher distingue "puerto ocupado"
  para mostrar error claro: "El puerto 4000 ya esta en uso".
- El usuario ve un mensaje claro: el launcher puede abrir un cuadro
  (msg / VBScript) si el backend no logra arrancar en 30 s.
- JWT_SECRET ausente: el backend muere al instante con mensaje claro
  (validacion B.2.1); el launcher lo captura y avisa "Revise la
  configuracion .env (JWT_SECRET)".

11. ACCESO DESDE CELULARES POR WIFI (puntos 17-20)
========================================================================
- Backend ya escucha en 0.0.0.0 (app.listen(PORT) sin host) -> listo.
- Red: el PC y los celulares deben estar en la MISMA red Wi-Fi.
- IP del PC (hoy): 192.168.1.90 (Wi-Fi). Las 169.254.x del listado
  son APIPA (sin DHCP): ignorar.
- URL del celular: http://192.168.1.90:4000  (misma app completa:
  login, POS, reportes; /api es relativo -> mismo origen -> sin CORS).
- Firewall de Windows (punto 18): regla de entrada para TCP 4000
  (perfil Privado; si la red Wi-Fi del minimarket figura como
  "Publica", agregar tambien ese perfil). Comando (futuro):
  netsh advfirewall firewall add rule name="LA PALMERA 4000"
  dir=in action=allow protocol=TCP localport=4000 profile=private
  (y profile=public si aplica). Verificar que la red Wi-Fi este
  marcada como "Red privada" en Windows (Configuracion > Red).
- IP fija (punto 19): reservar 192.168.1.90 en el router (reserva
  DHCP / direccion IP estatica) para que la URL del celular nunca
  cambie; documentar la IP en un cartel junto al PC.
- PWA en celular: el service worker necesita HTTPS; en
  http://192.168.1.90:4000 la PWA NO se registrara (la app funciona
  igual, sin instalacion/offline). Si se desea PWA instalable en la
  red local, habria que montar HTTPS local (certificado autofirmado
  + confianza manual en cada celular: mas complejo, opcional y NO
  necesario para el objetivo). Desde el propio PC, localhost SI admite
  SW (la PWA funciona en el PC con Chrome).
- Seguridad en red local: el acceso a la app sigue pidiendo login
  (auth intacta); el puerto 4000 solo estara expuesto en la red del
  negocio (no en Internet). Recomendacion: cambiar las contrasenas
  por defecto y no usar la red Wi-Fi publica del local si existe una
  red separada para empleados.

14. RIESGOS
========================================================================
- Puerto 4000 ocupado por otra app: el launcher debe avisar con
  mensaje claro (EADDRINUSE) en lugar de reintentar en bucle.
- Red Wi-Fi clasificada como "Publica" en Windows: la regla de
  firewall no aplicaria; se debe marcar como "Privada" o agregar el
  perfil publico.
- IP dinamica del PC: si el router no reserva 192.168.1.90, la URL
  del celular cambiaria; mitigacion: reserva DHCP + cartel.
- Router con "aislamiento de cliente" (AP isolation) activado:
  los celulares no verian al PC; desactivar esa opcion del router.
- PWA/offline no disponible via IP local (HTTPS): comportamiento
  esperado, documentado; no afecta el uso normal con conexion.
- Cierre forzoso del PC (corte de luz): sin datos corruptos (Atlas),
  pero los procesos quedan colgados; al reiniciar, el launcher detecta
  el puerto ocupado o lo libera con el script de cierre.
- Antivirus/Defender puede preguntar al primer lanzamiento del .cmd
  o bloquear el spawn oculto: aceptar en la maquina del negocio.
- Node no encontrado: el acceso directo debe usar la ruta absoluta de
  node.exe (verificar "where node" en el PC destino) y, si falta,
  mostrar instrucciones de instalacion (choco/installer oficial).
- Dos instancias del launcher abiertas a la vez: el launcher debe
  detectar el PID existente (logs/lapalmera.pid) y avisar "LA PALMERA
  ya esta abierta" en lugar de duplicar procesos.
- Cambios de codigo frontend futuros: recordar regenerar dist con
  npm run build (o el launcher lo hace automaticamente si dist no
  existe; opcional: comparar fechas).

========================================================================
1. Detener: doble clic en "Cerrar LA PALMERA" (o
   Stop-Process del PID en logs/lapalmera.pid).
2. Quitar accesos directos del Escritorio ("LA PALMERA" y
   "Cerrar LA PALMERA").
3. Quitar la regla de firewall:

   scripts/cerrar-lapalmera.cmd, scripts/instalar-accesos.cmd,
   scripts/desinstalar-lapalmera.cmd y la carpeta logs/.
5. Revertir el unico cambio de codigo en backend/src/app.js
   (eliminar el bloque express.static + SPA fallback) - o, si se
   prefirio git, restaurar ese archivo desde el ultimo commit.
6. Nada mas: no se instalo dependencias, no se toco .env, MongoDB,
   usuarios, auth ni package.json, por lo que no hay mas que revertir.
7. El desarrollo normal sigue funcionando intacto (npm run dev con
   vite + proxy), ya que la solucion local es aditiva.
